# metafaker

MetaFaker protects your privacy when you share photos. A photo straight from a phone or camera carries far more than the picture: the GPS position where it was taken, the exact time, the device's make and model, and, in the pixels themselves, a faint sensor pattern that can link it to the specific camera that took it. MetaFaker removes that identifying information before you share an image, either by stripping the metadata or by replacing it with a consistent, generated set that does not point to you.

It is for anyone who wants to share a photo without also sharing where they live, where they have been, or which device they own: journalists and the people they protect, activists, people selling things online, anyone who posts pictures publicly.

Everything runs locally in your browser. There is no backend, no upload step and no cloud storage, and the page makes **no network request at all** beyond loading its own files.

**What it protects, and what it doesn't.** It removes everything a photo's metadata says about you — location, time, device, serial numbers, the original filename — and gives every image its own unrelated identity. It does **not** remove the camera's sensor pattern: a processed photo can still be matched to the specific camera that took it by anyone who has a reference fingerprint of that camera, built from the device itself or from enough of your other photos taken with it. If that matters to you, take sensitive photos with a different phone or camera from the one whose photos you post under your own name. The picture itself also still matches its original. Details and measurements are under [Threat model and limits](#threat-model-and-limits).

## Current behavior

- Accepts multiple images from drag and drop or the file picker, decoded with
  `createImageBitmap`, which covers JPEG, PNG, WebP, AVIF and HEIC wherever the
  browser's codecs do (Safari decodes HEIC; Chrome without HEIC support gets a
  clear message to convert to JPEG). An undecodable file fails with a readable
  reason rather than silently.
- Tells a camera photo from a non-photo before generating any metadata. A
  screenshot or exported graphic never passed through a lens, so giving it a
  camera, lens and GPS would make it inconsistent with what it is. The decision
  uses the file's real format (read from its first bytes, not its name or
  MIME type), transparency, and its content: screens and graphics are full of
  perfectly uniform areas and sharp text edges on uniform backgrounds, which a
  camera sensor's noise never produces. Calibrated on 298 real camera photos
  and 26 real screenshots, each also as a messaging-app copy and as this tool's
  own output: no photo variant was taken for a screenshot, and 94% of
  screenshot variants were caught. Non-photos are cleaned of any identifying
  metadata instead — either a plain strip or an Adobe-exported graphic
  carrying editor provenance only, chosen at random so they do not share one
  signature, and never a camera or a location.
- Builds a local batch queue with previews (small copies, so large photos do not fill the tab's memory) and per-image state.
- Parses original EXIF locally in the browser.
- Re-encodes each processed image as a new JPEG through a privacy pipeline that removes identifying traces from the pixels, not only from the metadata.
- Either removes the metadata entirely or replaces it with a generated metadata set whose location is always inside the United States.
- Downloads processed files locally under a filename matching the generated camera.

## Privacy of the page itself

A privacy tool that phones home is not one. The page therefore:

- loads **no third-party resource**. The two libraries it uses (`piexifjs` 1.0.6 and `exifr` 7.1.3) are vendored under `vendor/`, not fetched from a CDN. A CDN-served module import cannot carry an integrity hash, so a compromised CDN could have run anything against the user's photos, and every visit handed the CDN the visitor's IP address and referrer. The icons are inline SVG rather than a Google-hosted web font, for the same reason.
- pins `vendor/piexif.js` with a Subresource Integrity hash, so the browser refuses to run it if its bytes ever differ from the reviewed file. `.gitattributes` keeps `vendor/` byte-for-byte, because a line-ending conversion changes the bytes and would break the hash.
- sends `Referrer-Policy: no-referrer`, so following a link from the page never reveals the page.
- offers a map link only for **generated** coordinates, pointing at OpenStreetMap with `noreferrer`. The original image's coordinates are the user's real position and are never linked anywhere.
- carries a Content-Security-Policy of `default-src 'none'` with `script-src 'self'`, as defence in depth behind the output escaping: EXIF from an untrusted image reaches the metadata panel, and if anything ever slipped through unescaped the CSP stops it executing.
- stores only the theme preference, in `localStorage` under `metafaker.theme`. Processed images, previews and queue state live in memory for the active tab only.

`tools/check.js` asserts the no-network property on every run: any request to a host other than the local test server fails the build.

## Running it

The hosted version is at https://0xs8n.github.io/metafaker/. The app is static, so you can also serve the directory with any static host (`python -m http.server`, GitHub Pages, nginx) and open `index.html`.

**To run it offline, open `dist/metafaker.html`** — one self-contained file with every script, style and library inlined, which works by double-clicking in any browser and can be copied to an air-gapped machine. Rebuild it after changing the source with:

```
node tools/build.js
```

Opening the modular `index.html` straight from disk does **not** work: browsers block ES module imports from `file://`, so the controller never loads and the buttons do nothing. If you open it that way, a message now says so and points you to the single-file build or to serving the folder, rather than leaving a dead page.

## Architecture

The application is split into small browser modules:

- `index.html` — the UI shell, upload zone, preview panel, action buttons and metadata panel.
- `css/style.css` — layout, batch queue, preview card, metadata table and toast styling.
- `js/main.js` — bootstraps the app, theme state, and wires drag/drop and file input events to the controller.
- `js/ui.js` — application state, queue management, rendering, downloads, and the processing workflow.
- `js/classify.js` — tells a camera photo from a screenshot or exported graphic before any metadata is generated, so a non-photo is never given a camera, lens or location.
- `js/exif.js` — generates the Adobe-export metadata set in each firmware's measured encodings (the per-make `WRITERS` profiles), parses source EXIF, verifies written metadata, and formats values for display.
- `js/data.js` — the camera database with the per-model EXIF facts measured from real files, and the lens database.
- `js/places.js` — the US place table every generated GPS position is drawn from, generated by `tools/build-places.js`.
- `js/provenance.js` — everything the file says about the editor that wrote it: its quantization tables, ICC profile, APP14 marker, the Photoshop APP13 block, and the XMP packet.
- `js/exif-writer.js` — the TIFF/Exif serialiser that replaces piexifjs's `dump`, little- or big-endian.
- `js/jpeg-requantize.js` — the baseline JPEG transcoder that re-quantises the browser's output onto the exporter's tables, adds its restart interval and APP14, and optimises the Huffman tables.
- `js/helpers.js` — shared utilities, the canvas pipeline, timezone and sun-position maths.
- `js/rng.js` — the one random source, backed by `crypto.getRandomValues`.
- `js/md5.js` — MD5, for the Photoshop IPTCDigest resource.
- `js/icons.js` — inline SVG icons.
- `js/boot-check.js` — a classic (non-module) script that shows a guidance overlay when `index.html` is opened from `file://` or the app otherwise fails to load.
- `vendor/` — the two pinned libraries.
- `tools/` — the test harness, the single-file build, and offline image-analysis measurement scripts.

`js/makernote.js`, `js/icc-profiles.js` and `js/qtables.js` hold measured data for a camera-original provenance that is **not wired in**; see the note at the top of each.

## Processing pipeline

For each loaded file:

1. The browser reads the input locally and decodes it once, to measure the content signals below and to make the preview the page shows, at most 1600 pixels on the long edge. Displaying the original itself made the browser decode it whole and keep it while it was on screen.
2. `exifr` parses the original metadata, and `js/classify.js` decides whether the input is a camera photo or a non-photo (a screenshot or exported graphic) from whether it names a camera, its real format, transparency and its content.
3. On `Randomize`, a photo gets a generated camera, lens, timestamps, exposure, location and editor identity from `generateFake()`, and the XMP packet is built from the same values. A non-photo is cleaned instead, as described above, and never given a camera or a location.
4. The image goes through the canvas pipeline in `js/helpers.js` and is exported as a fresh JPEG with the exporter's container.
5. `js/exif-writer.js` serialises the EXIF block and it is inserted into the JPEG.
6. The result is parsed back once more to verify the metadata was written before the output is offered for preview or download.

`Strip Current Metadata` runs the same pixel pipeline and writes the file as the same export with its metadata removed: no Exif, no XMP, no ICC profile, and the Adobe APP14 marker left in place, which is exactly what `exiftool -all=` leaves behind on a Camera Raw export. The earlier version left the ICC profile in, which produced a combination of segments that exists nowhere except in this tool's output. A non-photo takes the light path described below.

### Canvas pipeline

The canvas export is not a plain re-encode. Each photo passes through these stages so the output does not carry the sensor and encoder fingerprints that could link it back to the original photo or to the device that took it. Every parameter is drawn per image and several stages run on only a share of images, so there is no fixed recipe shared by every output that would link separately shared images to one another:

1. Proportional crop of up to 1.2% per edge, which shifts the sensor grid.
2. Rotation of 0.3 to 2.0 degrees in either direction on about two images in three, with a scale factor that keeps the frame filled.
3. Reshape onto a frame the generated camera can produce, then always downscale, by at least 8%, even when the image is already small. The long edge is drawn from real Adobe exports of the same kind of camera (679 phone and 2,521 camera-body exports on Wikimedia Commons, measured 2026-10-18, each uploader weighted equally), within three limits: 80 to 92% of the frame, the generated camera's own frame, which no export of it exceeds (a draw above it gives exactly the native size, as many real exports have), and 16 megapixels, which keeps the render's memory near what the old 3,200-pixel cap cost. Simulated on originals at each listed camera's own frame against those exports (`tools/check.js` asserts the share above 3,200 pixels), 71% of phone outputs and 73% of body outputs are above 3,200 pixels where none were before (68% and 69% of real exports), and the long edge alone now separates outputs from real exports with AUC 0.64 for phones and 0.67 for bodies, down from 0.82 and 0.76 (0.5 would be no separation). What is left is the input's limit, since a 12 MP original allows at most about 3,700 pixels, and the 16 MP ceiling: real body exports have a median of 5,472 pixels, outputs 4,539. Resampling onto a smaller grid weakens the sensor-pattern (PRNU) link between the photo and the camera that took it, but does not break it; see the threat model.
4. A non-rigid warp: a smooth random displacement field of under two pixels, built from three low-frequency waves with random directions and phases, followed by a light denoise. It is meant to weaken the sensor-pattern link further, since a field that varies across the frame has no single inverse to search for. Measured on real phones, its effect is small: the warp, denoise and fresh noise together cut the match score only about twofold.
5. Per-brand colour profile: warmth, saturation and contrast matched to the generated make. The saturation change is taken from a smoothed copy, so it reaches the picture's colours and not its fine colour grain; boosting every pixel also boosted the photo's colour noise.
6. ISP simulation: an anchored S-curve tone mapping on four images in five, and an unsharp mask of radius one or two pixels on three in four.
7. Lens optics: radial vignetting on seven images in ten and, on three in five, the residual lateral chromatic aberration a corrected lens leaves, a fraction of a pixel at the corner in either direction, sampled sub-pixel. It used to shift the colour channels by up to about 3 px with whole-pixel rounding, which misregistered colour across the whole frame.
8. Poisson-Gaussian sensor noise scaled to the generated ISO value (lower for camera bodies, whose sensors are larger), with the shot-to-read split drawn per image. It is built the way noise reaches a real export: a luminance field with a slight grain, plus a weaker, smoother chroma field, since demosaicing spreads each sample across channels and neighbours and the raw converter's colour noise reduction smooths most chroma away. The grain, the chroma share and its smoothness are drawn per image.
9. JPEG encode at quality 1.0 (the only setting at which the browser emits 4:4:4 chroma, which an export uses), then re-quantisation of the coefficients onto the exporter's measured tables, with rounding ties treated the same for both signs, and rewriting of the container: the browser's JFIF and ICC segments are removed and the exporter's ICC profile, XMP packet and APP14 marker are written in its order. (The re-quantiser used to round every tie the same way, which left one identical faint 8×8 pattern in every output, enough to tell them apart from real exports almost perfectly.)

A non-photo (a screenshot or exported graphic) takes a light path: crop, downscale (capped at 1600 pixels on the long edge) and a clean re-encode in the same export container. It has no sensor and no lens, so sensor noise, lens effects or a warp would only make it less like what it is.

Every random draw in the tool, from the camera down to the per-pixel noise, comes from `crypto.getRandomValues` through `js/rng.js`, refilled in blocks so the pixel loops stay fast.

### Large photos

The pipeline never holds the full-resolution picture while it works. It reads the input's size from its header, then asks the browser for the picture already scaled to twice the size it will be drawn at (`createImageBitmap` with resize options), and crops and scales it the rest of the way in one draw. Against drawing from the full-resolution decode, measured on 12 and 60 MP inputs at 2,048 to 7,000 pixels, an unrotated output is equally sharp and a rotated one 3 to 11% less sharp by the mean Laplacian, with no difference visible in 100% crops. Decoding only the cropped frame (a source rectangle) was lighter still but cost 8 to 26% of the sharpness, and Chrome placed the rectangle mirrored on a photo with EXIF orientation 6, so it is not used. The encoded file stays in byte arrays and Blobs from the encoder to the download, with no base64 copies, and the Adobe thumbnail is drawn from the finished canvas instead of decoding the output again. Measured in headless Chrome 155 on Windows 11 with `tools/peak.js` (the file handed to the page's own file input, one Randomize, the renderer's peak working set, three runs each, at the old size limit): a 12 MP iPhone photo went from 561 to 563 MiB down to 314 to 494, a 48 MP image from 970 to 1,072 MiB down to 455 to 555, and a 60 MP Sony A7R V export from 809 to 953 MiB down to 542 to 565. Most of the old peak was the page's own preview: an `<img>` showing the original decoded it whole and kept it while it was on screen. Chrome still decodes the whole file for a moment when the file is loaded and when it is rendered, so a 60 MP input still costs about 450 MiB at load. The time for one Randomize did not change measurably (9 to 18 s at 12 MP and 11 to 14 s at 60 MP after, 9 to 15 s and 10 to 36 s before, with other work running on the machine). Outputs are now drawn as large as real exports, up to 16 MP. Measured the same way on the 60 MP export, an output at that ceiling (4618x3464 or 4899x3266) peaks at 968 to 975 MiB and takes 21 to 32 s, within the worst the old 3,200-pixel cap reached (1,072 MiB); 6000x4000 had reached 1,226 to 1,553 MiB in an earlier measurement, which is why the ceiling is not higher. On a machine with less memory to spare, a large photo can still end the tab.

## Metadata generation

The generated metadata is built from static profiles rather than free-form values. The intent is internal consistency: metadata whose values contradict each other stands out, and a file that stands out draws attention to itself and to the person who shared it.

### Measured, not guessed

The camera facts in `js/data.js` and the Adobe facts in `js/provenance.js` were read from real files on Wikimedia Commons on 2026-10-16 with ExifTool: two camera originals per phone model, one per camera body, and seven Adobe exports (Camera Raw 16.3/16.4/16.5 and Lightroom Classic 13.4/14.0.1, plus Lightroom 7.1.2 and 6.5). On 2026-10-18 twelve newer models were added (iPhone 16, 16 Pro and 17 Pro, Pixel 9 and 9 Pro, Galaxy S25 Ultra, Canon EOS R5 Mark II and R6 Mark II, Nikon Z6III and Z f, Sony A7C II, Fujifilm X-T50) from 43 more camera originals (at least five per phone, from at least four uploaders each) and nine Adobe exports of the new bodies. The EXIF of about 100 further exports, as Commons reports it, showed what Adobe rewrites. Where a secondary phone lens was not among the samples, its figures are marked `approx` in the data file. Reproducing a measured rule beats inventing a plausible one: an iPhone 15 Pro writes its 6.765 mm focal length as the fraction `251773/37217` (the continued-fraction convergent of the float32 value), while a 14 Pro Max writes `343/50` for its 6.86 mm, and an export keeps each one, so the tool writes each model's own form. The same measurements show where the export does *not* keep the camera's form, and the tool follows the export there too (see Per-make encodings).

### Provenance

The output is written as a photo exported from an Adobe editor (for camera bodies, from a raw file; for phones, from a JPEG), not as a camera original, and that is deliberate. The editor is drawn per image as often as real exports name each one: of the exports dated 2024 or later on Wikimedia Commons, weighting each uploader equally, phones were exported with Lightroom Classic 68%, Lightroom (the cloud desktop app) 12%, Lightroom mobile 9%, Camera Raw 8% and the discontinued Lightroom 6 3% (391 files, 36 uploaders), and camera bodies with Lightroom Classic 56%, Lightroom 26%, Camera Raw 10% and Lightroom mobile 9% (1,510 files, 64 uploaders). Lightroom mobile, Lightroom 6, and Camera Raw for a phone JPEG are left out because their packets were not measured, and the rest renormalised: a phone output names Lightroom Classic 85% of the time and Lightroom 15%, a body output Lightroom Classic 61%, Lightroom 28% and Camera Raw 10%. Before this, every phone output named Lightroom and every body output Camera Raw, each the minority editor of its kind, which marked the outputs as a group.

A camera original has to carry a MakerNote. Real ones are large and model-specific, and an incomplete one would make the file internally inconsistent, whereas having none is ordinary: editors routinely drop it. An export is a story the file can tell completely: camera `Make` and `Model` intact, `Software` naming the editor, zero MakerNote tags, and a resolution below native. Photographers shoot raw and export, so this is among the most common files that exist.

The whole container is reproduced from the measured exports. The pixel section is the exporter's: one of the six quantization tables seen in clean desktop exports, drawn as often as real exports use each, a restart interval and restart markers, the 12-byte Adobe `APP14` marker before the frame header, optimised Huffman tables, and 4:4:4 chroma. After the start marker come the four metadata segments in the exports' order: the EXIF (little-endian, as every Adobe export is), the Photoshop `APP13` block, the `APP2` ICC profile (the 3144-byte HP sRGB profile), and the `APP1` XMP packet. `Software` names the release of that editor that was current at the export date (the newest about 85% of the time and one minor release behind most of the rest, as in real exports), with the matching `crs:Version`, on Macintosh or Windows in the measured shares (Camera Raw 21% Windows, Lightroom 36%, Lightroom Classic 38%). A body's export never names a release whose Camera Raw engine cannot open that body's raws. Lightroom Classic M.N writes `crs:Version` (M+3).N, measured on nine releases; its patch releases follow no one rule (13.5.1 writes 16.5, 14.3.1 writes 17.3.1, 15.2.1 writes 18.2.2), so `LRC_RELEASES` lists a patch only where its `crs:Version` was measured on a real export, and 15.1.1, whose export on Commons carries no develop settings, is left out. Only release strings seen in real exports are used, and the table has to be extended as Adobe ships new releases, or new outputs drift behind again; it was last measured on 2026-10-17. Document and instance IDs follow the platform: RFC 4122 version-4 UUIDs on Macintosh, as every Mac export measured writes, and plain random hex on Windows. The resolution is Camera Raw's 300 ppi or Lightroom's 240; Lightroom Classic exports at the user's setting, drawn as its exports show it (1,144 Commons exports dated 2024 on, 61 uploaders: 240 ppi 52%, 300 29%, 72 8%, 100 5%). The three editors write the same packet except where measured otherwise. Lightroom Classic adds `xmpMM:PreservedFileName`, the file's name at import (56 of 56 of its exports on disk since 13.0), and from 13.2 the pick flag `xmpDM:pick`, written unset (49 of 49 from 13.2 carry it, 43 of them unset; 0 of 7 before). Lightroom on Windows writes an `edited` history event before the export (8 of 10 of its Windows exports, 0 of 4 on Macintosh). The look's Copyright line is written by Camera Raw, Lightroom Classic from 14 and Lightroom from 9, and not by earlier releases. Nothing a user sets is reproduced: keywords, labels, ratings, pick flags, titles, copyright, and the City/State/Country that the address lookup fills in are left out. A user who renames files in Lightroom Classic leaves the new name in `crs:RawFileName` and the old one in `PreservedFileName` (25 of 49 exports); the tool's two names are always the same, since a user's own naming cannot be generated without inventing it, so that share is not matched. Its exports produce the same four `exiftool -validate` omission warnings as the others (55 of 56 on disk since 13.0, and the 6 downloaded for the release table), so the check holds for every editor.

An IFD1 thumbnail **is** embedded, because Adobe exports carry one: a 256-pixel image encoded the way the exporter encodes it (the standard Huffman tables, a 32-MCU restart interval, Adobe's APP14), and the same bytes appear again as the Photoshop thumbnail, as in the real files. (The thumbnail this tool briefly dropped, and before that embedded wrongly, had been encoded by the browser and carried Chrome's JFIF header and an ICC profile with the copyright string "Google Inc. 2016".)

The Photoshop `APP13` block carries the resolution-info resource, the IPTC record (the UTF-8 marker, record version 4, and the capture date and time with zone), the thumbnail resource, and the MD5 of the IPTC block as its IPTCDigest, exactly as the exports do.

The XMP packet carries what a real one carries, in Adobe's attribute order: `xmp:CreateDate` and `photoshop:DateCreated` at the capture time, `xmp:ModifyDate`, `xmp:MetadataDate` and the history entry at the **export** time, which is hours to weeks later; the `aux:` and `exifEX:` lens fields; a full `crs:` develop-settings block (a raw opens with Temperature/Tint and sharpening at 40, a JPEG with IncrementalTemperature and sharpening at 0); the four tone curves and the PointColors list, then from `crs:Version` 17.5 on the ColorVariance list (in 7 of 7 real exports at 17.5 to 18.2, none of 5 at 17.3.1 and 17.4); a `DerivedFrom` element that names the source by its own 32-hex ID twice and no instance ID, as every raw export and 25 of 31 desktop exports of a phone JPEG do (the `xmp.iid`/`xmp.did` form the phone path used to write appears only on sources another Adobe app had saved first, 2 of 31); the `AutoToneDigest` pair that pressing Auto leaves, at the share real exports carry it (16 of 31 JPEG exports, 12 of 37 raw exports), with a fresh value each time, since it is a digest of that image; and a history line naming the raw format the generated camera actually shoots (`image/x-canon-cr3`, `image/x-nikon-nef`, `image/x-sony-arw`, `image/x-fuji-raf`), or "saved to new location" for a phone JPEG. A raw export names the profile it opened with as real raw exports do: `Adobe Standard` with the `Adobe Color` look on top (28 of the 40 raw-source exports on disk), the look block copied from them, and the `CameraProfileDigest` of that body's own Adobe Standard profile. That digest is fixed per model (the same value in all 3 A7 IV exports, from three different Adobe editors, and in all 4 X-T5 exports), so it was read from real exports of each body; the earlier random digest matched no real profile, and two outputs of one body disagreed. The EOS 5D Mark IV, Z f, Z 6II and X100VI have no measured Adobe Standard digest yet (the exports found carry other profiles, or none were fetched) and are not offered until one is. The crop fields say what was done to the pixels: the pipeline crops every photo and straightens two in three, and `HasCrop`, the crop rectangle and `CropAngle` carry the crop and rotation it applied, in Adobe's convention (corners in normalised source coordinates, the rectangle turned by `CropAngle`, as measured on real straightened exports); they used to read "no crop, no rotation" over cropped and rotated pixels. Lens-profile correction is on in 29 of 40 real raw-source exports, but the profile it names is specific to the lens, so it is turned on, at that share, only for the five lenses whose Camera Raw profile was copied from a real export (data.js `lcp`), and only on bodies whose raws do not carry their own correction data (the Fujifilm bodies and the R5 Mark II do, and Camera Raw then records that shot's distortion model, which is not generated); for every other lens it stays off, with lateral CA removal at the share real exports with it off show (1 in 11). The packet is UTF-8 with a correct byte-order mark, the eight-space toolkit string Adobe writes, and the 4097-byte whitespace padding it appends.

A genuine Adobe export does not pass `exiftool -validate`: Adobe drops `ComponentsConfiguration`, `ExifImageWidth`, `ExifImageHeight` and `YCbCrPositioning`, and a Samsung or OnePlus phone writes `OffsetTime` and `LensModel` with an `ExifVersion` older than the spec allows for them. The output carries those same four omissions and, for those phones, those same version mismatches, so it produces the **same** validation warnings a real export does and no others. Matching the real file means matching its imperfections, not scoring better than it.

### Consistency rules

- **Per-make tag sets.** An export preserves the camera's tags, so a file presenting as a Samsung has to carry Samsung's tag set, not a generic one. The per-make `WRITERS` profiles in `js/exif.js` record which optional tags that firmware writes (which `SubSecTime` tags and at what width, `SensingMethod`, `SceneType`, `FileSource`, `CustomRendered`, the contrast/saturation/sharpness trio, `DigitalZoomRatio`, `LightSource`, `GainControl`, Nikon's `CFAPattern`, the CIPA sensitivity pair, which lens tags) and the values it uses (`MeteringMode`, the `Flash` codes for "did not fire"). Per model, `ExifVersion`, built-in flash, raw format and `OffsetTime` support are fixed, not drawn; the `OffsetTime` tags only exist from Exif 2.31, so a 0220 writer never carries them. Canon never writes `FocalLengthIn35mmFormat`; Apple writes no `MaxApertureValue`; Nikon writes `Flash` as 0; the Qualcomm-based Android makers write `ExifVersion` 0220. `FlashpixVersion` is always 0100. `ColorSpace` is always sRGB, because the export is.
- **Per-make encodings.** Each firmware serialises its rationals its own way and the export carries most of them through. Apple writes arbitrary-denominator rationals produced from floats and reduced fractions (`343/50` for a 6.86 mm focal length); Canon reduces exposure compensation in thirds; Nikon writes compensation in unreduced sixths; the Android makers and Fujifilm write over 100; a body's focal length keeps the camera's own denominator, unreduced (`470/10` from a Nikon, `1590/100` from a Fujifilm). `DigitalZoomRatio` is the firmware's own "no zoom" value: `0/1` from a Pixel, `100/100` from a Galaxy, `16/16` from a Sony. An iPhone writes it only when zoomed, in 33% of US-located iPhone photos, as the frame's short side over the cropped one, reduced (`3024/1511`), and scales `FocalLengthIn35mmFormat` by it; the tool draws the ratio from those photos and does the same. A zoomed Pixel photo writes its own ratio while keeping the lens's 35 mm equivalent; that is not reproduced, and Pixels always write `0/1`. Some values are rewritten by the exporter, and those follow the export instead: `FNumber` is always a decimal (`18/10` for an iPhone's f/1.78, `56/10`, `8/1`), the APEX shutter and aperture values are over 1000000, reduced by tens where they can be (`784549/100000`), a Canon lens's `MaxApertureValue` is on Canon's eighth-stop scale as a decimal (`3/1` for f/2.8, `175/100` for f/1.8), and a body's `FocalPlaneResolution` is the exact value Camera Raw's exports of that body carry (`55369938/32768` per cm for a Z6III). GPS coordinates are also the **exporter's**: degrees plus decimal minutes to four places with a zero seconds field, because XMP stores them as `DDD,MM.mmmmN` and the exporter reconciles that back into EXIF.
- **Manufacturer spellings.** Samsung writes `samsung`, Nikon writes `NIKON CORPORATION` and `NIKON Z 9` with a space, Sony writes `SONY`.
- **The sun fixes the scene.** The location is drawn first and the capture time is drawn against the sun there on that date, as real US phone photos are taken (`tools/capture_times.js` over 2,999 US-located Commons phone photos from 212 uploaders): a photo in daylight takes a measured point between sunrise and sunset, one after sunset a measured time since it. People shoot earlier on short days, so a fixed clock-hour mix, even the measured one, put 16% of photos after civil dusk and 30% in December; this puts 10.6% there against the real 10.4%, and the shares at -6 to 0, 0 to 8, 8 to 25 and above 25 degrees of sun come out within a point of the real ones. For a phone, the sun's elevation at that place and time then picks the scene brightness: no daylight exposures after dark. A camera body's brightness is instead that of a real body export taken at the same time of day (the capture hour each file in the body table carries, in three-hour bands with the night from 21:00 to 06:00 as one), and after dusk only of one at EV 10 or darker. Body exports are darker than phone photos all day, not only at night: between 09:00 and 18:00, 19% of them are at EV 13 or brighter (2,144 exports from 119 uploaders), where bodies drawn from the phones' scene model came out at 42 to 45%. Bodies go to talks, events and museums, and most of their exports carry no location to measure the sun against, so they are measured against the clock. The exposure is then a real photo's at that brightness, from `js/exposure-tables.js` (built by `tools/exposure_tables.py` from Wikimedia Commons surveys read on 2026-10-18, every uploader weighted equally): a phone takes the time and ISO of a phone photo of its family (Apple: 1,598 files from 186 uploaders; Android: 1,098 files from 22 uploaders, almost all Pixels) shot through a lens of about its own f-number, whose exposure gives the scene's EV within half a stop; a body takes the f-number, time and ISO of one of 2,144 Adobe exports of body photos (119 uploaders), among those its lens opens to and its shutter and ISO range allow. Every uploader counts once, but no single file may carry more than a fifth of the files a draw is made from: the half-stop window widens a quarter stop at a time, up to a stop, until none does, and past that the weights are capped. Where few uploaders shot a given brightness, one file from a single-file uploader had carried up to 89% of the Android draws (at EV 8), so the outputs at that brightness repeated its exposure; over 6,000 generated identities the median effective number of files behind an Android draw went from 4.9 to 9.9 and the lowest tenth from 1.4 to 5.9 (Apple 13.5 and 2.3 to 14.7 and 6.8, bodies 15.0 and 3.8 to 15.7 and 9.7), while the phone exposure-time quartiles moved from 1/100, 1/250 and 1/1600 s to 1/100, 1/290 and 1/1500 s (real 1/98, 1/295 and 1/1845) and the EV quartiles stayed within 0.1 of their values. The phone files are all located in the United States, because a phone locks its exposure time to the mains flicker: US phone photos sit at exactly 1/60 s in 11% of files and at 1/120 s in 12%, and at 1/50 or 1/100 s, the 50 Hz times, in under 1%, while photos taken elsewhere sit at 1/50 in 8%. The time is then written the way Camera Raw and Lightroom write it, through a port of the DNG SDK's `SnapExposureTime` (`js/exposure.js`): within 2% of a standard speed it snaps to it, otherwise it is rounded on a grid that coarsens with speed, so a firmware's 1/1215 s becomes 1/1200 and a Pixel's 2101/1000000 becomes 1/480. `ShutterSpeedValue` and `ApertureValue` are mirrored from the written `ExposureTime` and `FNumber` as the SDK mirrors them; `BrightnessValue` comes from the camera's own time.
- **Lenses have to fit.** Bodies list the mounts they accept and lenses declare theirs. The lens is chosen before the exposure, and only exposures at f-numbers it can open to are drawn. `LensSpecification` carries the lens's real range, with Canon's apertures left empty, which current Camera Raw writes as 0/0. A fixed-lens body reports no lens model; F-mount Nikon glass reports through the MakerNote only, so the D850 carries no lens tags in EXIF and the export names the lens in XMP in Adobe's own `24.0-70.0 mm f/2.8` form.
- **Phone optics are per lens.** `FocalLength` carries the real focal length and `FocalLengthIn35mmFormat` the equivalent. Apple's `LensSpecification` spans every lens on the back.
- **GPS agrees with the place.** Altitude is the place's ground elevation ±20 m, below sea level where the ground is (`GPSAltitudeRef` 1 in El Centro). `GPSTimeStamp` is UTC derived from the capture time through the place's own timezone, DST included, with matching `OffsetTimeOriginal` where the model writes it. `GPSVersionID` follows the exporter, which normalises it: Camera Raw writes 2.3.0.0 (7 of 7 real exports), Lightroom 2.2.0.0 (5 of 5) and Lightroom Classic 2.2.0.0 (23 of 26). Canon bodies also carry `GPSStatus` and `GPSMapDatum`, as Canon's firmware writes them.
- **Every image is its own identity.** `Randomize Entire Batch` gives each image exactly what `Randomize Current` gives it: its own camera, lens, city, capture and export dates, editor version and filename, drawn independently. Images processed together share nothing through their metadata, so they cannot be linked to each other, or grouped as coming from one person, by a common device, place, trip or naming sequence.
- **Dates follow real exports and do not leak the run.** Exports are drawn from the two years before an anchor that itself sits a random one to ninety days in the past, so the latest date in an output does not say when the tool was run. The capture comes first, at a drawn time of its own (see The sun fixes the scene), and the export follows it by a measured delay, at a measured export hour when the delay is a day or more. Drawing the export first and the capture back from it put a third of the photos exported within a day after dusk, where real ones exported that soon are still daytime photos. The export hour and the delay follow what 4,688 real exports on Wikimedia Commons show, weighting each of their 169 uploaders equally: 40% are exported within a day of capture, half within two days, one in ten more than 110 days later. The camera is always one that was on sale by the capture date, and for bodies that report a firmware version, that firmware existed too. A camera body's export also never names a Camera Raw older than the first release that opens that body's raw files, taken from Adobe's supported-cameras list (16.4 for an EOS R5 Mark II, for example); a body whose first supporting release is newer than every release in the table is not offered at all. `Keep original date and time` makes the output's Date Taken the original's exact date and time (from `DateTimeOriginal`, else `CreateDate`, else the last-saved date), and so links it to the original; use it only when that moment is not sensitive. Every other date is drawn to fit after it, as for a generated date: the export follows the capture by a measured delay, the camera and editor version existed by then, and no date is later than now in the generated place's own time zone. A photo taken within the last day or so is exported between its capture and now, rather than before the anchor, and is placed only where its wall-clock time has already happened. The risk is shown inline under the checkbox once it is ticked, not only in a tooltip, and randomizing a batch with it ticked reports how many outputs end up sharing a calendar day, since that links them to each other too. A date that cannot be kept consistently gets a new one, and the page says why: the file has no capture date, it is older than every camera the tool can name (a photo from 2001), or it has not happened yet in any US time zone. The day used to be kept with a fresh time, and a recent photo was always exported exactly 30 minutes after its capture; `tools/check.js` now asserts both behaviours away.
- **Byte layout.** ASCII values are padded to an even length, sub-IFDs carry their next-IFD terminators, tags are sorted. Output is checked with `exiftool -validate`, which reports exactly the warnings a real Adobe export produces (see Provenance) and no others.

Generated locations come from `js/places.js`: the 4,228 US places of 10,000 people or more, 210.9 million people in all (62% of the US population), incorporated places with their Census 2024 population estimate and census-designated places (Honolulu among them) with their 2020-2024 American Community Survey estimate. `tools/build-places.js` generates the table from public-domain Census, NWS, USGS and IANA files. Each image draws a place weighted by population, then a point uniformly in that place's disk, independently of every other image. A disk is the largest that fits inside the place's Census boundary, on US land at least 150 m inside the 1:500,000 Census shoreline, inside one time zone, and within the place's settled radius of its GNIS town centre: the radius of its land area, or of the area its population would fill at 1,000 people per square mile, whichever is smaller, so that Anchorage's disk sits on the city and not in the Chugach Mountains that make up most of its land. Radii run from 255 m to 20 km, median 1.6 km. The build samples every disk on its rim and inside and refuses to write the table if any sample leaves the place, US land, its time zone or the land mask `tools/us-land.json`; `tools/check.js` tests every output's GPS, and 3,000 positions drawn from the generator, against that mask. Two places are left out: Guttenberg, NJ, too small for a 250 m disk, and Ontario, OR, which lies in a forecast zone split between Mountain and Pacific time.

Measured on 3,000 identities from the generator, classified against the Census state boundaries and Natural Earth's Mexico and Canada: the previous list of 58 city centres, each jittered in a 0.1° square, put 41 (1.4%) in Mexico or Canada, El Paso's square reaching into Ciudad Juárez and Detroit's into Windsor, and 140 (4.7%) in water; the place table puts none in either. The table's elevation is the USGS 3DEP ground elevation (Elevation Point Query Service) at each disk's centre. Against the ground at 300 drawn positions it is within 6 m for half of them, 40 m for nine in ten, and up to 490 m off where a disk takes in hills its centre does not share (El Paso's takes in the Franklin Mountains). The time zone is the NWS forecast zone's code, read as one IANA zone per code; the build checks that every US zone in the IANA database keeps the same UTC offsets as its code's zone from 2016-09-08, the oldest camera's release and so the earliest capture date, to two years ahead. Only `America/Metlakatla` differs (Pacific time in the winter of 2018-19), and the Annette Island Reserve has no place in the table.

## Export format

- Output files are always JPEG.
- The original filename is never used, in the download name or anywhere inside the file. Each photo gets a generated source filename in its camera's own convention, recorded in the XMP as `crs:RawFileName` (`DSC_4821.NEF` for a Nikon, `DSC04821.ARW` for a Sony, `DSCF4821.RAF` for a Fujifilm, `IMG_0734.HEIC` or `IMG_0734.JPG` for an iPhone (HEIC 40%, `.JPG` 25%, `.jpeg` 25%, `.JPEG` 10%: the source names kept in 16 desktop exports of iPhone photos from 10 uploaders, none of them a lowercase `.jpg`; a HEIC is recorded as converted to JPEG, as all 10 real exports of one are), `PXL_20240612_141503123.jpg` for a Pixel, `20240612_141503.jpg` for a Samsung), and `getOutputName()` in `js/ui.js` names the download after that same stem with a lowercase `.jpg`, as a real Adobe export is. Date-based names use the generated capture time, and the Pixel's millisecond field is the frame's `SubSecTime`. A file with no generated camera — a metadata-stripped output, or a non-photo exported as an Adobe graphic — carries no capture date to echo, so it gets a random, time-free stem instead; the real clock the tool ran on is never in a filename. `tools/check.js` asserts that the input's filename appears nowhere in the output's bytes, and that no download name carries a date within a day of the run.

## Threat model and limits

What this tool does and does not protect against, stated plainly, because the people who need it most are the ones who will be hurt by overclaiming.

- **Metadata.** Everything the original carried is gone: Exif, XMP, IPTC, MakerNote, ICC, embedded thumbnails, trailers such as Samsung's and Google's motion-photo data, C2PA manifests. The output's metadata describes a camera, place and time that are not yours.
- **Encoder fingerprints.** The browser's quantization tables, JFIF header and ICC profile are replaced with a real exporter's. Each output uses one of the exporter's measured tables and its ICC profile, as real Adobe exports do.
- **Sensor pattern (PRNU): not removed.** Every camera sensor leaves a faint, unique noise pattern in its photos. Anyone with a reference fingerprint of your camera — built from the device itself, or from enough of your other photos taken with it — can check whether a processed photo came from it. Measured on real phones from the VISION dataset: all 22 processed outputs of an iPhone 6 still matched that phone (match scores 506 to 17,235, where 60 is the standard threshold; a second iPhone 6 of the same model scored at most 20), and so did 15 of the 16 matchable photos from a 12 MP Huawei P9. The downscale, warp, denoise and fresh noise weaken the pattern about twofold but do not remove it; offline, even shrinking to 0.3× left it matchable. Processed photos from the same phone can sometimes also be linked to each other without the phone (22 of 91 pairs in one test). **What protects you:** take sensitive photos with a different phone or camera from the one whose photos you post under your own name, or that could be taken from you.
- **Machine-learning image-analysis models** (TruFor, Noiseprint++, CAT-Net and the like) have not been tested against this output. The pipeline reproduces the statistical traces of an ordinary camera photo, but no claim is made about how these models assess it.
- **The picture itself matches its original.** The visible content is unchanged, so perceptual hashes and reverse image search will match a processed photo to its original and to other processed copies of it (median distance 2 to 6 bits out of 64). If the original was ever shared or uploaded anywhere, the processed version links to it. No tool can prevent this without changing the picture. Unrelated photos stay unrelated (about 30 of 64 bits apart).
- **Recognisable as a group.** Analysed together, many outputs may still be told apart from ordinary photos. The strongest sign, a faint 8×8 pattern every output shared, is fixed (see step 9 of the pipeline): measured on real phone photos, a detector built on it went from separating outputs from real files almost perfectly (AUC 0.995) to 0.74, where 0.5 would be indistinguishable, so a weaker trace of unidentified origin remains. Other population-level differences found in the same evaluation have since been corrected from real-export measurements: the Adobe version now fits the export date, the platform split, IDs, quantization tables and export hours follow real exports. The added noise used to be more colourful than a real camera's, independent per channel on phones. Measured with `tools/noise.py` on 44 real camera files and Adobe exports from Wikimedia Commons, each compared with a plain downscale of itself to the output's size and quantization tables, the phone outputs' chroma-to-luminance noise ratio went from 0.24 above that reference to 0.05 above, and the correlation between their R, G and B noise from 0.26 below it to 0.02 below; the camera-body outputs, whose noise had been per-pixel white, now carry a grain within 0.02 of the reference. The overall noise level varies between runs of this size by several tenths of a level and is not shown to match. The camera list was last extended on 2026-10-18 and stops at models released by September 2025 (the iPhone 17 Pro); generated dates run up to the present, so as newer models spread, a file naming an older camera becomes slightly less ordinary. Exposure times follow Adobe's one-pass rounding, which produces 669 of 670 real phone-export and 2,143 of 2,146 body-export `ExposureTime` values on Commons (the rest are encodings Adobe does not write); whether Lightroom Classic 13 to 15 moved to the DNG SDK 1.7's two-pass rule, which differs only near 1/1300 s, is not known. The exposure follows real files at the same scene brightness and f-number, and since the capture time follows the sun the phones' EV quartiles match real US phone photos (7.6, 11.2 and 13.9 against 7.8, 11.3 and 13.9), but the phones' brightness still comes from an unmeasured scene model, which puts phones at 0 to 8 degrees of sun at a median EV of 7.5 against 9.6 for real ones; the bodies' comes from real body exports, and their EV quantiles (5, 25, 50, 75 and 95%) are 4.9, 7.0, 9.6, 11.8 and 14.3 against 4.9, 7.0, 9.9, 12.0 and 14.6 for the exports (3.6, 7.3, 11.3, 14.0 and 15.3 on the phones' model), and a phone's lens is drawn as often as real US phone photos use it (`PHONE_LENS_SHARES` in `js/data.js`: the main camera in 69% of iPhone photos on models with a telephoto and 91% on those without, where a uniform draw gave 33 to 67%). So over 6,000 generated identities the phone exposure-time quartiles are 1/100, 1/290 and 1/1500 s against 1/98, 1/295 and 1/1845 for real US phone photos (1/100, 1/250 and 1/1600 before no file could carry more than a fifth of a draw, 1/65, 1/250 and 1/1400 with uniform lenses, 1/60, 1/180 and 1/1200 before the capture time followed the sun), their f-number and ISO quartiles are f/1.7, 1.8 and 1.9 and ISO 32, 50 and 200 against f/1.6, 1.8 and 1.8 and ISO 32, 50 and 130, 8% of phone exposures are 1/30 s or slower against 6% (16% before the capture time and the lens shares were measured), and 22% of body exposures are at f/8 or narrower against 17% of real body exports (34% on the phones' scene model, 45% before the exposure was drawn from real files). What remains is the lens mix: the lenses offered do not open as wide as those in the real exports, so the draw falls back on files shot at narrower apertures, and with the lens limit lifted the same draw gives 17.2% at f/8 or narrower; the same cause leaves 12% of body exposures at 1/30 s or slower against 7% (5% with the limit lifted).
- **The generated location is plausible, not a sample of where photos are taken.** Places are weighted by population, which stands in for where people take photos; no dataset of US photo locations was used. Places under 10,000 people, and the 38% of Americans who live outside them, are never drawn. Every output lies inside one of 4,228 published disks, which anyone with the source can test. A coordinate outside all of them is not an output; one inside is somewhat more likely to be one than an arbitrary US photo is, by an amount not measured here. Inland water that the 1:500,000 Census boundaries count as land, such as the Detroit and Niagara rivers and lake shores, is not removed: 5 of 3,000 draws fell inside a Natural Earth lake outline (62 before), all on such rivers and shores.
- **Image content** is yours to check: faces, reflections, signage, documents, screen contents, and anything that contradicts the generated location or season.
- **Downloads carry their origin.** Browsers record where a file came from in filesystem metadata outside the file (`Zone.Identifier` on Windows, quarantine and "where from" attributes on macOS). The file's bytes are clean; the download record is not. The offline single-file build opened from disk avoids the web origin, and the hosted page says so in a note by the Download buttons, hidden on the single-file build itself since it has nothing to warn about.
- **Linking across a batch.** Every image, in a batch or on its own, draws an independent identity, so the metadata gives no common device, place or date to link images to one another. Their content still can: the same scene, objects or people across several photos link them regardless of metadata.

## Testing

```
node tools/check.js
```

Launches headless Chrome, processes every image in `testimg/` (synthetic images carrying sensor-like noise, since real photos cannot be redistributed here) plus a set of non-photo cases (a PNG screenshot, the same screenshot as JPEG, a PNG renamed `.jpg`, an SVG, a transparent WebP, and the tool's own screenshot output loaded again) and an extensionless JPEG with no MIME type, and asserts: the output's structure byte by byte (segment order, no JFIF, the Adobe thumbnails, a correct XMP byte-order mark, no browser strings anywhere in the file); that the page made no request to any host but the test server; that images randomized as a batch each get their own identity; that every non-photo case is classified as a non-photo and given no camera, lens or location, and that no camera photo is taken for a screenshot; that the input's filename appears nowhere in any output; that 3,000 locations drawn from the generator all lie on US land; and, when `exiftool` is installed, that each file produces only the validation warnings a real Adobe export does, that its GPS is on US land (`tools/us-land.json`), that its dates, exposure and sun position are consistent, and that no browser-encoded data survives. Over 1,000 generated identities it also asserts that every exposure time is one Adobe's rounding produces, with the APEX values mirrored from it, and that times and ISOs, as written, follow the real files at the same EV and f-number as an export of them writes them. Fields that depend on the camera or are written at a share cannot be seen in a handful of outputs, so it also builds 400 generated XMP packets in the page and asserts on those: every body carries Adobe Standard, its own measured profile digest and the Adobe Color look, and ColorVariance appears exactly from `crs:Version` 17.5, lens-profile correction names only the profile measured for that lens, and some exports have it on; DerivedFrom has the measured shape, and the AutoToneDigest pair appears at the measured share, never repeated. The editor families must come out at their shares; Lightroom Classic packets carry exactly its own fields (the name at import, and the pick flag from 13.2), Lightroom on Windows its `edited` event, and the look's Copyright line only the editors that write it; no body names a release too old to open its raws; and iPhone sources are named as real ones are. For each photo output it also checks that the XMP crop rectangle and angle, applied to the input's dimensions, give the output's own shape.

`node tools/stress.js <inDir> <outDir>` runs both the randomize and strip paths over a folder of edge-case inputs (tiny, boundary and odd sizes, panoramas, grayscale/CMYK/progressive JPEG, WebP, RGBA and screenshot PNGs) and reports the classifier verdict and any failure per file. See `tools/README.md` for this and the offline pixel-domain measurements.

## Runtime dependencies

Both are vendored and pinned; nothing is fetched at runtime.

- `vendor/piexif.js` — piexifjs 1.0.6, for reading EXIF back and inserting the APP1 segment. Its serialiser is replaced by `js/exif-writer.js`.
- `vendor/exifr.esm.js` — exifr 7.1.3, for parsing. `vendor/exifr.umd.js` is the same library in the form the single-file build inlines.

There is no build step for the multi-file version. `node tools/build.js` produces the single-file one.
